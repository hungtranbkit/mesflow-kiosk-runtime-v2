# Security

**Status: SECURITY_ARCHITECTURE_PASS (design), NOT PRODUCTION_SECURITY_PASS.**
Per the task's own §59: do not read anything below as "security enabled."
Device identity/provisioning state IS implemented and live-verified
(docs/PROVISIONING.md). mTLS, certificate storage, secure boot, and flash
encryption are DESIGNED in this document only — no code for
`CertificateStore`/`TlsClientConfig` exists yet, and transport remains
plain HTTP, same as Phase 0. This is an honest gap, not an oversight to
paper over.

## Threat model (basic)

- **Physical access assumption**: a kiosk sits on a shop floor with
  unsupervised physical access. The serial console (USB) currently accepts
  unauthenticated `wifi:`/`api-endpoint:`/`provision:`/`suspend:`/`revoke:`
  commands — fine for a dev bench, NOT acceptable for a fielded device
  without at minimum a physical-access control (locked enclosure) and
  ideally an authenticated provisioning flow.
- **Network assumption**: the kiosk's Wi-Fi network is not assumed trusted.
  Plain HTTP (Phase 1) means anyone on that network can observe or tamper
  with event/heartbeat traffic. This is the single biggest gap between
  current state and production-ready — see "Transport" below.
- **Backend compromise/impersonation**: nothing in this codebase yet
  verifies the backend's identity beyond DNS + a URL a human typed in. A
  hostile/spoofed backend on the same network could currently receive real
  business events. mTLS (below) is the intended fix, not built yet.
- **Supply chain / firmware integrity**: no secure boot, no signed
  firmware. A device with physical flash access can run arbitrary firmware
  today. Out of scope to fix this phase (Phase 6 — OTA/secure boot).

## DEV vs PROD build profile (implemented, verified)

Two profiles, decided at COMPILE time, never at runtime (`MESFLOW_PROFILE_DEV`/
`MESFLOW_PROFILE_PROD`, `build_info.h`, `scripts/build-dev.sh`/`build-prod.sh`):

| | DEV | PRODUCTION |
|---|---|---|
| `/debug/*` (screenshot/ui-state/device-state/input) | compiled IN | compiled OUT entirely (not just disabled at runtime) |
| Backend URL scheme | http:// or https:// | https:// only (`BACKEND_URL_ALLOW_HTTP`) |
| Verbose logs | on | on (no secret ever logged in either profile — see below) |

Verified: `strings` on the compiled `.elf` shows 4 occurrences of
`/debug/screenshot`/`/debug/ui-state`/`/debug/input` in the DEV build and
**0** in the PROD build — a real compiled-artifact check, not just "the
flag is set." Both profiles build clean (`scripts/build-dev.sh`/
`build-prod.sh`). PROD has not been flashed to the dev board this
session (not required — §70 explicitly allows build+host verification).

**No eFuse is burned by anything in this repository. No Secure Boot/Flash
Encryption is configured or enabled.** JTAG/download-mode policy is
untouched (default/open) — appropriate for a DEV board, not yet designed
as an actual production checklist (that's a real deliverable still
missing, see "Known gaps").

## Device identity (implemented, verified — docs/PROVISIONING.md)

`hardware_id` (immutable-ish, from eFuse MAC) and `device_id` (business
identity, empty until provisioned) are two different things, stored in
their own NVS namespace (`kiosk_identity`), separate from Wi-Fi/backend
config (`kiosk_v2`) and the sequence high-water-mark (`kiosk_seq`).
Invariant 12: no shared/default fleet identity.

## mTLS architecture — DESIGNED ONLY, not implemented

Target:

```text
DeviceIdentity  (implemented, but for device_id/hardware_id/provisioning_state
                 only -- NOT extended to hold certificate material this phase)
CertificateStore  (NOT IMPLEMENTED -- would hold: client cert, private key,
                    server CA, all in NVS, none ever logged or exposed via
                    /debug/*)
TlsClientConfig   (NOT IMPLEMENTED -- would configure WiFiClientSecure with
                    the above and wire it into api_client/bootstrap_client/
                    heartbeat_client in place of the current plain WiFiClient)
```

Flow (design, not built): device cert + private key + server CA → mTLS
handshake via `WiFiClientSecure` → `HTTPClient` using that secure client
instead of plain `WiFiClient`. A DEV path (self-signed dev CA + dev server
cert + per-device dev client cert, generated by a script, never committed
as if real) would prove the mechanism before any real PKI exists. None of
this was built this phase — `/debug/device-state`'s `security.mtls` field
honestly reports `"DESIGNED_NOT_ENABLED"`, not `"ENABLED"`.

## Certificate lifecycle (data model, documented — not implemented)

```text
certificate_id, issued_at, expires_at, status
ACTIVE -> EXPIRING -> EXPIRED -> REVOKED
        \-> ROTATING -> (new cert validated) -> ACTIVE, with a rollback
            window kept until the new cert is proven working
```
No code exists for this yet — recorded here so Phase 1's identity work
doesn't back itself into a design that can't support rotation later
(e.g. `DeviceIdentity` deliberately doesn't hardcode "one cert forever").

## Transport (current reality: still plain HTTP)

`api_client`/`bootstrap_client`/`heartbeat_client` all use plain
`HTTPClient`/`WiFiClient` — no TLS validation, no mTLS, no per-device
identity on the wire. Do not point this firmware at anything beyond a
trusted local mock or a public test endpoint (this session used
`httpbin.org` for live verification specifically because it's a trusted
public echo service, not because arbitrary internet endpoints are an
appropriate target in general).

## No remote data becomes code (invariant 4, unchanged from Phase 0)

UI bundles, config, and commands are data interpreted by a fixed,
whitelisted runtime. Never: JS, Lua, C, dynamic bytecode, `eval`, shell.

## No secret logging (§27/§34, implemented and reviewed)

Reviewed every `log_structured`/`/debug/*` call site this phase: Wi-Fi
password is never passed to any log or JSON response (`/debug/device-state`
exposes SSID/RSSI/IP only). `structured_log` itself has no special-casing
for secrets — the discipline is "never construct a message containing one"
at every call site, checked by inspection, not enforced by the logger.

## Known gaps (do not overclaim)

- No production eFuse/Secure-Boot/Flash-Encryption checklist exists yet —
  "documented eFuse burn procedure, reviewed before use" from Phase 0's
  SECURITY.md draft is still just that draft, not written.
- No PIN/auth on DEV serial provisioning commands.
- No CertificateStore/TlsClientConfig code — mTLS is 100% design.
- No signed OTA / signed UI bundle (both later phases; no bundle engine or
  OTA mechanism exists at all yet for there to be anything to sign).
